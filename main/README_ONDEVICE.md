# 设备上真正执行的东西

这个仓库只有 `main/ksu` 一个文件需要拷进手机。它不是脚本，也不是可执行 elf，是**一个前面带 shell 头、后面挂压缩载荷的复合文件**。

## 为什么做成一个文件

常见的写法是把载荷拆成目录：一个 sh 加四五个二进制，靠一个入口脚本去读。那种结构在 `adb push` 一次的时候没问题，但在这台机器上踩过两个坑：

- `push -a` 不保证保留权限位，`gl_v112` 推进去是 `0644`，跑起来 `Permission denied`
- 中途被系统的清理任务删掉一半，入口脚本报的错是「找不到文件」，看不出是哪一件丢了

所以这里把四个载荷压进同一个文件尾部。代价是这个文件 5.7 MB，好处是**只有一次传输、没有第二个依赖**。

结构上是这样：

| 段 | 范围 | 内容 |
|---|---|---|
| shell 头 | `1 .. 17572` | 整个控制流程，`#!/system/bin/sh` 可执行 |
| 载荷 | `17573 ..` | gzip 流，解开是 tar，里面四件 |
| 四件 | — | `lt/gl_v112`、`dl/ksu_raw.ko`、`dl/libksud.so`、`dl/allowlist.bin` |

`PAYLOAD_OFFSET=17573` 写在脚本第 55 行左右，是构建时算出来的，不要手改。想验证这个常量对不对，用 `tools/unpack.sh`，它会照着脚本里这个值去切，切完核对四个 md5。

## 四种用法

拷到 `/data/local/tmp/ksu`，`chmod 755`，然后：

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `sh ksu` | 完整越狱（五步） | 正常情况 |
| `sh ksu check` | 只报状态，不动任何东西 | 不确定现在是什么状态时先跑这个 |
| `sh ksu clean` | 删日志、临时目录、四个载荷 | 想留个干净现场 |
| `sh ksu relax` | 只把 SELinux 切宽容，后面不做 | 只想验证喷射能不能打中 |

`check` 是只读的，它只打印四行：模块加载没有、内嵌载荷数量、本开机用掉的槽位、常驻的 `gl_v112` 进程号。**这四个信息足够判断要不要重启。**

## 一次成功运行会经过五步

脚本每一步都会打 `n/5`，卡在哪一步一眼能看出来。

**1/5 把 SELinux 设成宽容。** 这一步是硬依赖，不能和第 2 步并行 —— `enforcing=1` 的时候读 `sig_enforce` 直接 `Permission denied`，读不出来就没法判断签名校验状态。命中判据是 `/sys/fs/selinux/enforce` 变成 `0`，脚本轮询 12 秒。

**2/5 关掉模块签名校验。** 判据是 `/proc/sys/kernel/module/sig_enforce` 变成 `N`。这里用的槽位序列和 1/5 不同，见下一节。

**3/5 复查。** 这一小步不写任何东西，只是再读一遍。读出来不是 `N` 就 `die`，**不会走到 `insmod`**。这是刻意的：签名校验没关就装载模块，内核直接 Oops 重启，回头什么日志都没有。

**4/5 提权、装载模块。** 拿到 `uid=0` 之后：从 `gl_v112` 的侧信道结果算出 KASLR slide，拼出 `kln=0x<静态地址+slide> level=3`，`init_module` 把 `ksu_raw.ko` 送进去，再用 `prctl(0xDEADBEEF, 7, 1, 0, 0)` 让模块把 `allowlist.bin` 读进内存。这一步给的超时是 25 秒，比前三步宽，因为要做的动作多。

**5/5 等模块自己把 `enforcing` 写回 `1`。** 模块的 `enforce_after` 参数默认是 1，装载完自动收尾。脚本最多等 10 秒；等不到只打一行提示，不判失败 —— 因为这时候模块已经在了，扫尾慢一点不影响结果。

五步全过之后：后台派发 `me.weishu.kernelsu` 的管理器（`am start` 大约 20 ms 返回，所以放在后台，先打结论再开界面），然后清掉临时目录和载荷。

## 槽位：为什么要记台账

喷射打的是内核栈上的固定偏移，但**同一个偏移在同一台机器上不一定每次都中** —— 栈上有没有别的东西、深浅多少，和当时的进程状态有关。所以每次尝试从一个候选偏移里挑一个，没中就换下一个。

三组候选是写死的：

| 用途 | 候选序列 |
|---|---|
| `selinux` | `0x240 0x440 0x0c0 0x040 0x6c0 0x740` |
| `cred` | `0x680 0x700 0x740 0x6c0 0x780 0x540` |
| `sig` 及其它 | `0x680 0x700 0x740` |

三个序列不一样不是随便写的：`selinux` 那一步要落的是 `selinux_state` 附近的指针，`cred` 那步落的是 `task_struct` 的 cred 指针，两者的落点特征不同，同一个偏移在两边命中率不一样。`sig` 走的是最后一个 `*` 分支，也就是默认序列，共三个候选。

台账在 `/data/local/tmp/.ksu_slots`，每行记 `boot_id` + 用掉的槽位。**为什么要带 `boot_id`**：槽位是一次开机内的资源，重启就清空。如果不记 `boot_id`，重启之后再跑脚本会以为槽位还在用、直接报「用尽」，逼你手工删台账。现在的写法是读 `/proc/sys/kernel/random/boot_id` 比对，不是本次开机的行自动忽略。

槽位耗尽的表现是 `slot_for` 返回空，脚本打「槽位用尽，只能重启」，然后 `die`。**这时候唯一正确的动作是重启手机**，不要手删台账 —— 手删了脚本会去重试已经证明不中的偏移，白跑一轮还更慢。

## 产物、日志、清理

| 路径 | 是什么 | 什么时候消失 |
|---|---|---|
| `/sdcard/Download/ksu_last.log` | 本次运行的完整日志 | 下次运行覆盖 |
| `/data/local/tmp/k1.log` `k2.log` `k4.log` | 各步喷射程序的原始输出 | 下次运行前清掉 |
| `/data/local/tmp/.ksu_slots` | 槽位台账 | 不清也不影响，重启后旧记录按 `boot_id` 自动失效 |
| `/data/local/tmp/gl_v112` 等四件 | 从尾部解出来的载荷 | 运行结束自动删；`clean` 也删 |

日志优先写 `/sdcard/Download`，写不进去（比如没授权存储）会退回 `/data/local/tmp/ksu_last.log`。所以如果 `/sdcard/Download` 里找不到 `ksu_last.log`，先去 `/data/local/tmp` 看一眼，别以为脚本没跑。

失败的时候不用手翻 `k1.log`：脚本自己会把该步日志的末两行打出来，前面带四个空格缩进。

## 症状对着看

| 屏幕上看到的 | 实际发生了什么 | 怎么处理 |
|---|---|---|
| `1/5 三次都没命中` | 试了三个 selinux 槽位都没打中（序列共六个，还有余地） | 直接再跑一次，栈状态会变 |
| `2/5 三次都没命中` | 三个 sig 槽位试完没中 | 同上；如果连续两轮都不中，重启 |
| `sig=Y` 然后 `已中止` | 第 3 步复查没过，没做 `insmod` | 这是保护，重新跑即可，没有副作用 |
| `4/5 四次都没命中` | cred 槽位用掉四个还没拿到 root | 脚本提示「SELinux 仍是宽容状态」，再跑一次；cred 还剩两个 |
| `槽位用尽，先重启` | 台账显示本次开机候选全部用掉 | 重启手机，不要删台账 |
| `5/5 仍是 enforce=…` | 模块装着但没写回严格模式 | 只有这一行提示，不算失败；`getenforce` 复查，必要时手动 `setenforce 1` |
| `内核模块已加载，跳过利用` | 之前已经成功过 | 这是幂等的，不是错 |

## 不该做的事

- **不要杀常驻的 `gl_v112` 进程。** `check` 里那一行 `常驻 gl_v112 进程: <pid>（刻意保留，勿杀）` 是认真的。那个进程是提权链路留下的引用点，杀掉之后模块的某些回调会失效，表现为 su 能用但模块功能半死。
- **不要手动 `insmod` `ksu_raw.ko`。** 缺 `kln=` 参数，模块里的符号解析会拿到 0，装载成功但所有 hook 都是空指针，随后在第一次 su 时崩。
- **不要把 `ksu_raw.ko` strip 掉再装。** 仓库里那份是 4.7 MB、带完整 `.debug_*` 的原始件，和设备上验证通过的那一份逐字节相同。strip 之后体积能小到 1/8，但那就不是验证过的东西了，出问题没法 `addr2line`。
- **不要改 `PAYLOAD_OFFSET`。** 那个值是构建时按实际头部长度算的，改一位就切不准，`unpack` 会拿到半个 gzip 流。
